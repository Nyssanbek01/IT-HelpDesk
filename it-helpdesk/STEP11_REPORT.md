**Политика расчёта:**

| Приоритет | Первая реакция | Решение |
| --- | --- | --- |
| high | 15 минут | 4 часа |
| medium | 60 минут | 8 часов |
| low | 240 минут | 24 часа |

Все сроки отсчитываются от createdAt по календарному времени 24/7. Расчёты используют UTC/миллисекунды; браузер выводит даты в своём часовом поясе.

Реакция — первое успешное действие «Взять в работу» через engineer API. Простое назначение администратором реакцией не считается. Инженер может взять новую неназначенную заявку или новую заявку, назначенную ему. Существующее право admin действовать через engineer API сохранено: такое фактическое взятие также фиксирует реакцию. После переназначения/снятия инженера дедлайны и первая реакция не сбрасываются. Реакция фиксируется условным обновлением только при null и надёжном отслеживании с создания; проигравший захват ничего не фиксирует. resolvedAt — первое успешное изменение статуса на resolved; повторное завершение сохраняет дату.

**Исторические данные.** Существующим заявкам заполнены только дедлайны по createdAt и priority. Их slaTrackedFromCreation=false, firstRespondedAt и resolvedAt не выдумываются. Для исторической реакции возвращается unknown. Для старой решённой заявки без resolvedAt SLA решения также unknown и исключается из процента соблюдения. Для старой активной заявки срок решения известен и может отображаться как ожидающий/просроченный; если её впоследствии решат, новое достоверное resolvedAt будет записано. Worker консервативно не рассылает SLA-уведомления по всем legacy-заявкам, чтобы не создавать исторических ложных предупреждений. Если новая заявка решена без зафиксированного взятия, SLA реакции остаётся unknown.

**Статусы каждого этапа:**

| Статус | Значение |
| --- | --- |
| on_time | Этап ещё не выполнен, до зоны предупреждения есть время |
| approaching_deadline | Осталось не более 20% исходного интервала, но окно предупреждения не меньше 5 минут |
| overdue | Этап не выполнен, серверное время достигло или превысило deadline |
| met | Достоверное время выполнения не позже deadline, включая точное равенство |
| breached | Достоверное время выполнения позже deadline |
| unknown | Нет необходимого дедлайна/достоверного времени или неизвестна историческая реакция |

После выполнения этапа met/breached вычисляются по сохранённым датам, поэтому перезапуск сервера не меняет результат. Если worker впервые увидел уже просроченный этап, создаётся только overdue, без запоздалого approaching_deadline.

**API:**

| Endpoint | Изменение |
| --- | --- |
| `POST /api/tickets` | Сервер устанавливает createdAt и дедлайны; попытка передать SLA-поля возвращает 400 |
| `GET /api/tickets`, `GET /api/tickets/:id` | SLA только собственных заявок по существующей политике доступа |
| `GET /api/engineer/tickets` | `sort=newest|resolutionDueAt`, `slaStatus=all|on_time|approaching_deadline|overdue|met|breached|unknown`, `slaStage=any|response|resolution` |
| `PATCH /api/engineer/tickets/:id/take` | Однократная фиксация реакции в успешной транзакции; поддержано взятие назначенной себе новой заявки |
| `PATCH /api/engineer/tickets/:id/resolve` | Однократная фиксация resolvedAt |
| `GET /api/admin/tickets` | Те же slaStatus/slaStage, совместно с прежними поиском, фильтрами и пагинацией |
| `GET /api/admin/sla/stats` | Новая аналитика, только JWT + актуальная роль admin; неожиданные query отклоняются |
| Детали и ответы изменения заявки engineer/admin | Содержат сохранённые SLA-поля и вычисленный объект sla |

Объект `sla` содержит `serverNow`, `response` и `resolution`; каждый этап содержит status, dueAt, completedAt и remainingMs (null для неизвестного или завершённого этапа). При `slaStage=any` фильтр означает совпадение хотя бы одного этапа. Сортировка resolutionDueAt ставит активные заявки перед решёнными, внутри каждой группы — ближайший дедлайн, затем ID; null-дедлайны последними в своей группе. Политика доступа общей очереди инженеров не изменялась.

Статистика возвращает activeTickets, responseOverdue, resolutionOverdue, approaching (число заявок, не сумма этапов), resolvedOnTime, resolvedBreached, eligibleResolved, unknownResolved, compliancePercent и responseCompliancePercent. Overdue считает ещё невыполненные этапы; уже выполненный с опозданием этап имеет breached. Основной процент в интерфейсе явно назван «Соблюдение SLA решения»: resolvedOnTime / (resolvedOnTime + resolvedBreached), с округлением до одного знака; при отсутствии достоверных решений null. Неизвестные старые решения не ухудшают процент. Отдельный responseCompliancePercent учитывает только достоверные завершённые реакции.

**Worker и уведомления.** Создаются типы sla_response_approaching_deadline, sla_response_overdue, sla_resolution_approaching_deadline, sla_resolution_overdue. Получатели: автор, назначенный инженер и текущие администраторы, только если актуальная роль даёт доступ к заявке. Произвольные инженеры не получают SLA-рассылку. Инициатор системного уведомления — null. Текст шаблонный, без комментариев, содержимого файлов, паролей и токенов.

Каждая проверка блокирует строку Ticket через FOR UPDATE, повторно проверяет текущий статус/даты и пишет уникальное событие вместе с Notification в одной транзакции. Поэтому повторные проверки и несколько worker-процессов не создают дубликаты. Та же блокировка координируется с захватом и изменениями заявки. После реакции предупреждения о реакции прекращаются; после resolved прекращаются все предупреждения. Новые события не создаются для неизвестного этапа. Ошибка откатывает событие и уведомления; следующий цикл безопасно повторяет проверку.

Запуск из backend:

```powershell
# Постоянный отдельный процесс: последовательная проверка, затем пауза примерно 60 секунд.
npm.cmd run sla:worker

# Одна проверка и выход.
npm.cmd run sla:worker -- --once

# Проверка всех SLA-сценариев с управляемыми часами, без реального ожидания дедлайнов.
npm.cmd run test:sla
```

Worker не зависит от открытого браузера. Он запускается явно отдельно от API; постоянный сервис/планировщик ОС автоматически не устанавливался. SIGINT/SIGTERM останавливают цикл и закрывают Prisma. Поддерживается несколько экземпляров благодаря уникальному ключу в БД и транзакциям. Одноразовый запуск проверен: `checked: 0, events: 0, notifications: 0` — на момент аудита все рабочие заявки были legacy, поэтому рассылка корректно не выполнялась.

**Frontend.** Общий TicketSla показывает обе стадии, точные дедлайны и фактические даты, цветовые индикаторы и неизвестные значения. Обратный отсчёт обновляется раз в минуту от серверного remainingMs с монотонным performance.now, поэтому неверные часы компьютера не меняют его. Статусы не вычисляются клиентом. На активных деталях серверный SLA перечитывается раз в минуту; на списках обновляется список. Если отсчёт дошёл до нуля без нового ответа, интерфейс сообщает, что статус уточняет сервер, и сам не объявляет нарушение. При resolved, недоступности и размонтировании таймер деталей останавливается; запросы отменяются при размонтировании.

Сроки есть в пользовательских списках/деталях и обзоре, в списках/деталях engineer/admin. Engineer Dashboard по умолчанию сортируется по ближайшему сроку решения, выделяет просрочки и имеет SLA-фильтр. Admin Dashboard содержит SLA Analytics с процентом, показателями и быстрыми ссылками на проблемные заявки. Фильтр администратора сохраняется в query, поэтому быстрые ссылки открывают правильную выборку. Ширина 360px проверена без горизонтального переполнения.

Проверены A–P из задания. В частности, конкурентность проверялась на настоящих транзакциях PostgreSQL: два одновременных take дают один 200 и один 409, а два одновременных checkSla создают одно событие соответствующей стадии/фазы. Первая реакция не меняется после снятия/переназначения и повторного взятия. Даты сохраняются при новом Prisma-подключении. Первая дата решения не меняется при повторном завершении. Проверены 1 мс до дедлайна, точное равенство и 1 мс после, независимые этапы, 20%/5 минут, UTC, JWT, роли, чужие заявки, запрет SLA-инъекции, сортировка/пагинация/фильтры, процент и unknown.

SLA-тесты используют управляемый серверный clock и явно заданное время worker, без ожидания реальных дедлайнов. Браузерный тест управляет минутными callbacks и performance.now, намеренно задаёт неправильный Date.now и проверяет, что только серверный ответ меняет статус. Также проверены локальный часовой пояс Asia/Qyzylorda, остановка таймера после удалённого решения и logout, взятие назначенной себе заявки и адаптивность. Браузерные тесты используют production-сборку с подменённым API; интеграционные backend-тесты — реальные маршруты/JWT/PostgreSQL.

**Сохранность и очистка.** Каждый SLA integration-запуск создаёт 5 уникальных временных пользователей и 7 временных заявок. Удаляются только точные ID этого запуска и их события/уведомления/история. SHA-256 снимков существующих User, Ticket, TicketComment, TicketHistory, TicketAttachment, Notification и TicketSlaEvent до/после совпал. Регрессионные тесты уведомлений также очистили только собственные записи. Полный набор запускается последовательно, чтобы независимые интеграционные тесты не влияли на снимки друг друга. Профили браузера и временные файлы тестов очищены. Существующие аккаунты, заявки и вложения не удалялись. Миграция намеренно добавила только новые SLA-поля и заполнила дедлайны.

**Ограничения.** Считается календарное время 24/7; календарь рабочих часов не добавлен. Старые реакции остаются неизвестными, legacy-рассылка подавлена намеренно. Аналитика и вычислительные SLA-фильтры пока используют выборку кандидатов в память на сервере; для большой базы понадобится SQL-агрегация/фильтрация. Обновление UI занимает примерно минуту; worker отправляет уведомления в ближайшем успешном цикле, а не гарантированно в точную миллисекунду дедлайна. Проценты отображаются только для достоверных завершённых этапов. Правила доступа общей очереди инженеров сохранены. Email/SMS, WebSocket, AI, платные сервисы и сложные рабочие календари не добавлены.
