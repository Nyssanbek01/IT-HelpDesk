Шаг 10 — система уведомлений IT HelpDesk. Завершено 13 октября 2026.

**Результат.** Уведомления сохраняются в PostgreSQL и отображаются в общей верхней панели user, engineer и admin. Email, SMS, WebSocket, push, AI, SLA и платные сервисы не добавлялись. Существующие TicketHistory и защита конкурентного захвата сохранены.

**Миграция:** `20261013090000_notifications`. Добавлена таблица Notification с recipientId, nullable actorId/ticketId, type, title, message, isRead, createdAt и readAt. Добавлены индекс `(recipientId, isRead, createdAt, id)` и индекс createdAt. Удаление заявки сохраняет уведомление и обнуляет ticketId; удаление инициатора обнуляет actorId; удаление получателя удаляет его уведомления. Миграция применена через migrate deploy. Старые миграции не менялись; migrate reset не запускался. Prisma Client сгенерирован, migrate status показывает актуальную БД, migrate diff — отсутствие различий.

**Новые endpoints, все требуют JWT:**

| Endpoint | Поведение |
| --- | --- |
| `GET /api/notifications?page=1&limit=20&unreadOnly=false` | Только свои записи, createdAt DESC / id DESC; items, total, page, limit, totalPages. limit 1–100, page 1–1 000 000; строгая валидация query |
| `GET /api/notifications/unread-count` | `{ count }` для текущего получателя |
| `PATCH /api/notifications/:id/read` | Только своё уведомление; повторный вызов сохраняет первоначальный readAt |
| `PATCH /api/notifications/read-all` | Только свои непрочитанные записи; `{ updated }` |

ID получателя всегда берётся из проверенного JWT и актуальной записи User. Чужой ID уведомления возвращает 404; некорректные параметры — 400; отсутствующая/удалённая сессия — 401; ошибки хранилища — 500. Попытка подменить recipientId в query списка отклоняется; тело PATCH не влияет на получателя. Ответы не содержат паролей, токенов, email инициатора, storageKey или файловых путей. Для уведомлений недоступных или удалённых заявок возвращается нейтральное сообщение, ticketId и type обнуляются; права проверяются по актуальной роли, а не роли старого JWT. Ответы имеют Cache-Control: no-store.

**Правила отправки:**

| Событие | Получатели |
| --- | --- |
| ticket_created | Все пользователи с актуальной ролью engineer, которым доступна общая очередь |
| ticket_assigned | Назначенный инженер и автор заявки |
| ticket_taken | Автор заявки |
| ticket_resolved | Автор заявки |
| new_comment от user | Назначенный инженер, если он существует и имеет доступ |
| new_comment от engineer/admin | Автор заявки |
| attachment_added | Другая сторона по тем же правилам, что для комментария |
| ticket_unassigned | Автор и прежний инженер, если они имеют доступ |

Инициатор всегда исключается; получатели дедуплицируются и проверяются по текущей роли и правилам доступа. Для неназначенной заявки комментарии/вложения пользователя не рассылаются произвольным инженерам. Тексты состоят из серверных шаблонов и номера заявки: заголовок заявки, комментарий, содержимое и исходное имя файла в уведомление не копируются. Уведомления записываются в той же транзакции, что успешное создание/изменение заявки, комментария или вложения. Повторное назначение тому же инженеру, повторное завершение, проигравший захват и отклонённые действия не создают уведомлений.

**Frontend.** NotificationBell содержит счётчик, выпадающий список, различие прочитанных и непрочитанных записей, заголовок/текст/дату, чтение одного и всех, пагинацию по 10 записей, loading/empty/error/retry. Перед переходом выполняется авторизованный GET соответствующей заявки, чтобы обработать удаление или отзыв доступа. Маршруты: `/tickets/:id`, `/engineer/tickets/:id`, `/admin/tickets/:id`. JWT передаётся только в Authorization. Есть закрытие по Escape и клику вне панели, фокус при открытии и возврат фокуса при Escape, aria-label и aria-expanded. dangerouslySetInnerHTML не используется.

Polling выполняется примерно раз в 30 секунд после завершения предыдущего цикла. Один планировщик последовательно выполняет запросы и операции чтения; повторные обновления объединяются. Дополнительное обновление происходит при открытии панели и после успешных действий с заявками, комментариями и вложениями через общий apiFetch. При logout/размонтировании таймер очищается, запросы отменяются, обработчик события удаляется.

**Ручная проверка через браузер:**

1. Запустите backend/frontend через `npm.cmd run dev`. В отдельных профилях браузера войдите как user, engineer и admin.
2. Создайте отдельную проверочную заявку пользователем. Откройте колокольчик инженера: должно появиться «Новая заявка»; у автора нет уведомления о собственном создании.
3. Назначьте инженера администратором. Проверьте уведомления у инженера и автора. Повторное сохранение того же назначения не должно добавлять уведомлений.
4. На отдельной неназначенной проверочной заявке выполните «Взять в работу», затем завершение. Автор получает соответствующие события. После reload они сохраняются.
5. Напишите комментарий и загрузите файл от каждой стороны: уведомляется другая сторона. Для неназначенной заявки произвольные инженеры не получают комментарий/файл пользователя.
6. Проверьте «Отметить прочитанным», «Прочитать все», счётчик и переход к заявке. Удалите только проверочную заявку: её уведомления сохраняются и показывают понятное сообщение о недоступности.
7. Проверьте открытие Enter, закрытие Escape, ширину 360px, обновление после открытия и примерно через 30 секунд. После logout запросы `/api/notifications` должны остановиться.
8. Удаляйте только созданные для ручной проверки записи; существующие данные не используйте для проверки удаления или изменения ролей.

**Известные ограничения.** Обновление между пользователями происходит через polling, поэтому без открытия панели задержка составляет примерно 30 секунд плюс длительность запроса. В существующей модели проекта все инженеры имеют доступ к общей очереди; отдельного признака приватной заявки или ACL для инженеров нет, новая система не меняет эту модель. Исторические действия до применения миграции не создают уведомлений задним числом. Каждая успешно созданная новая заявка/комментарий/загрузка — отдельное событие; универсальные ключи идемпотентности POST в существующем API не добавлялись. Автоматической очистки старых уведомлений нет.
