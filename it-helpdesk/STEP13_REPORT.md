**Новые endpoints, все только для JWT + актуальной роли admin:**

| Endpoint | Ответ |
| --- | --- |
| `GET /api/admin/analytics/overview` | Создания, решения, текущая нагрузка, неизвестный исторический срез, средние, распределения, SLA решения |
| `GET /api/admin/analytics/tickets-trend` | Хронологические buckets с created/resolved, включая нулевые интервалы |
| `GET /api/admin/analytics/engineers` | Текущие инженеры, текущая активная нагрузка, достоверно атрибутированные решения/средние/SLA, покрытие атрибуции |

| `GET /api/admin/analytics/export` | Агрегированный CSV по тем же фильтрам, из одного транзакционного снимка |

Query-параметры: `dateFrom`, `dateTo` в ISO-формате YYYY-MM-DD; `interval=day|week|month`; опциональный положительный `engineerId` актуального инженера. Неизвестные параметры, повторные значения, некорректные даты/ID/интервалы, перевёрнутый или превышающий 366 дней диапазон возвращают 400. По умолчанию — последние 30 календарных дней UTC, включая текущий день. При указанном только dateTo берутся 30 дней до него включительно; при только dateFrom конец — текущий UTC-день. В ответах есть нормализованный range: dateFrom/dateTo, fromInclusive, toExclusive, asOf, timezone, interval, engineerId. Будущие события не включаются.

Границы: `[dateFrom 00:00:00 UTC, день после dateTo 00:00:00 UTC)`, дополнительно событие должно быть не позже текущего серверного now. Событие ровно в now допускается. Неделя начинается в понедельник UTC, месяц — с первого числа. Первый/последний недельный или месячный bucket может быть неполным относительно выбранного периода. Метки графиков — даты UTC, без сдвига в часовой пояс браузера.

**Формулы и смысл метрик:**

| Метрика | Формула / когорта |
| --- | --- |
| created | COUNT сохранившихся Ticket с createdAt в периоде и не в будущем |
| resolved | COUNT с достоверным resolvedAt в периоде, resolvedAt >= createdAt, не в будущем; дата создания может быть вне периода |
| activeNow | Текущее число status != resolved, независимо от дат периода; отдельный показатель текущей нагрузки |
| activeAtPeriodEnd | null + пояснение: полная история состояний не гарантирована, текущее состояние не выдаётся за историческое |
| statuses/priorities | Текущее распределение заявок, созданных за период; явно подписано как текущее состояние когорты создания |
| averageResponse | AVG(firstRespondedAt − createdAt) в мс для созданных за период, slaTrackedFromCreation=true, firstRespondedAt >= createdAt и событие до конца периода/не позже now |
| averageResolution | AVG(resolvedAt − createdAt) в мс для достоверных событий решения за период; отрицательные интервалы исключаются |
| SLA решения | met / (met + breached) × 100, округление до одного знака; met: resolvedAt <= сохранённого resolutionDueAt, breached: позже; неизвестный deadline не входит в знаменатель |
| SLA реакции | Аналогично по созданной когорте, достоверному firstRespondedAt и responseDueAt; legacy, отрицательные, ещё не выполненные и неподтверждённые этапы исключаются из знаменателя |

Средние возвращаются вместе с числом образцов; при их отсутствии — null, а не выдуманный ноль. Доли всегда возвращают числитель и знаменатель; при нулевом знаменателе percent=null. Ожидающие и неизвестные реакции отображаются отдельной объединённой категорией и не считаются соблюдёнными. Известные времена сравниваются с уже сохранёнными SLA-дедлайнами согласно Шагу 11, без нового расчёта сроков и изменения правил реакции.

Старые resolved-заявки без resolvedAt нельзя достоверно отнести к периоду. Они не включаются в решения, тренд или процент; `unplacedResolvedGlobal` отдельно показывает их общее количество во всей системе. `excludedResolutionEvents` показывает некорректные отрицательные интервалы решения в выбранном периоде во всей системе, независимо от фильтра инженера. Эти исключения явно подписаны в интерфейсе и CSV.

**Инженеры и атрибуция.** Для решения используется единственный distinct actorId события TicketHistory `status_changed → resolved`, oldValue не resolved, с createdAt не раньше создания заявки и в пределах ±5 секунд от достоверного resolvedAt. Допуск учитывает небольшую разницу между серверной меткой и временем транзакции БД; отсутствие события, слишком большой разрыв или противоречивые actorId оставляют исполнителя неизвестным. Текущий assignedEngineerId не используется для исторической атрибуции.

Таблица включает пользователей с текущей ролью engineer. Для каждого: имя, текущие активные назначения, число достоверно выполненных им решений за период, среднее и SLA с долями. Решения неизвестного исполнителя и решения исполнителей вне текущего списка инженеров (например, admin или сменивший роль пользователь) показаны отдельными числами, а не приписаны другому инженеру. Количество обращений подписано как нагрузка, а не единственная оценка эффективности.

Фильтр engineerId имеет разные явно объяснённые основания: создания/распределения/средняя реакция — текущее назначение когорты создания; решения/среднее решения/SLA решения — подтверждённый исполнитель истории; активная нагрузка — текущее назначение. Поэтому, например, переназначение после решения не переносит результат решения в статистику нового инженера.

**Графики:**

1. Линии «Создано» и «Решено» по day/week/month, хронологически, с generate_series и нулевыми периодами.
2. Столбцы текущих статусов созданной когорты.
3. Столбцы приоритетов созданной когорты.
4. SLA реакции: выполнен, нарушен, ожидает/неизвестно.
5. SLA решения: выполнен, нарушен, неизвестно.

У каждого графика есть текстовое пояснение, aria-label и доступная таблица точных чисел. Рабочие значения берутся только из API. Категории с отсутствующим положительным счётчиком отображаются нулём; случайные или тестовые значения не подставляются.

Установлен **Chart.js 4.6.1**: используются только line/bar controllers, необходимые scales/elements и legend/tooltip, без React-обёртки и date-adapter. Это позволяет одной зависимостью строить все требуемые графики; поддержка выборочных импортов описана в [официальной документации Chart.js](https://www.chartjs.org/docs/latest/getting-started/integration.html). Страница загружается через React.lazy отдельным chunk, около 176,74 КБ / 61,80 КБ gzip вместе с кодом аналитики; остальной интерфейс не загружает графики при первом входе.

**Frontend.** Фильтры периода, группировки и инженера сохраняются в URL. Используются существующие apiFetch и JWT в Authorization; токен не попадает в URL. Старые запросы отменяются AbortController, результат дополнительно привязан к ключу текущего запроса. При смене фильтров старые графики скрываются; поздний старый ответ не заменяет новые данные. CSV-запрос также отменяется при смене фильтров/размонтировании. Есть loading/error/retry, пустой период, отсутствие инженеров и отсутствие достоверных средних/процентов. Дизайн сохранён, таблица и графики адаптированы к 360px, имена выводятся текстом без HTML-инъекции.

**CSV:**

- Те же dateFrom/dateTo/interval/engineerId и один RepeatableRead snapshot для всех разделов.
- UTF-8 с BOM, comma-separated, CRLF, 5 фиксированных колонок, кавычки/запятые/CR/LF корректно экранируются.
- Все ячейки проходят csvCell: префиксы `=`, `+`, `-`, `@` нейтрализуются апострофом, включая скрытие за пробелами, BOM, Unicode format/control characters; начальные управляющие символы также защищены.
- Content-Type `text/csv; charset=utf-8`, Content-Disposition attachment с безопасным именем из проверенных дат; X-Content-Type-Options nosniff.
- Только агрегаты и имена инженеров; нет email, паролей, JWT, описаний/заголовков заявок, storageKey и приватных путей. Методика и исключённые исторические данные включены отдельными строками.
- Размер ограничен: максимум 366 дней, до 1000 текущих инженеров и 5 МБ готового CSV; превышение инженерного/байтового лимита — 413. Это обоснованная ограниченная сводная выгрузка, а не неограниченный dump заявок.

Реальная настольная Excel-сессия не автоматизировалась; проверены BOM/UTF-8, заголовки, экранирование и download. При необходимости в Excel используйте импорт CSV с UTF-8 и разделителем «запятая», поскольку региональные настройки разделителя могут отличаться.

**Производительность и БД.** COUNT, AVG, FILTER, GROUP BY, date_trunc и generate_series выполняются в PostgreSQL. CTE выбирают только необходимые поля, необработанные заявки не загружаются в Node.js для подсчёта. Для сложных агрегатов используются только параметризованные Prisma.sql/$queryRaw; пользовательские даты/ID/interval не конкатенируются в SQL. Список инженеров строится пакетными агрегатами workload/performance, без N+1. Каждый JSON endpoint использует RepeatableRead; CSV — единый такой снимок по всем разделам.

**Ручная проверка:**

1. Запустите backend/frontend через npm.cmd run dev. Войдите администратором и откройте «Аналитика» или /admin/analytics.
2. Выберите период до 366 дней, day/week/month, инженера. Сопоставьте «Создано» с createdAt, «Решено» с достоверным resolvedAt; обратите внимание на разные когорты и подписи текущего состояния.
3. Проверьте таблицы «Данные графика», нулевые интервалы, числители/знаменатели SLA и неизвестные значения. Обновите страницу: фильтры должны сохраниться в URL.
4. Нажмите «Экспорт CSV», проверьте файл в Excel/редакторе с UTF-8, включая кириллицу и поля методики. JWT в URL отсутствует.
5. Выберите пустой период, ошибочный диапазон, медленную сеть и быстро смените фильтры; старые графики не должны заменять новые. Проверьте ширину 360px.
6. Войдите как user/engineer и попробуйте /admin/analytics: доступ закрыт. Прямые API-запросы также требуют admin и JWT.
7. Для расчётных примеров используйте npm.cmd run test:analytics: он создаёт и очищает собственные записи. Не изменяйте рабочие даты/назначения ради проверки.

**Ограничения.** Аналитика строится по сохранившимся записям; удалённые заявки не восстанавливаются. Исторический activeAtPeriodEnd намеренно недоступен без полной надёжной истории. Атрибуция консервативна: окно ±5 секунд и единственный actorId; неизвестные исполнители не заменяются текущим назначением. Список инженеров отражает текущую роль, прочие известные исполнители вынесены в отдельный счётчик. UI endpoints читаются отдельными запросами, поэтому при одновременных изменениях возможны небольшие различия между их моментами снимка; CSV согласован в одной транзакции. Период ограничен 366 днями, список — 1000 текущими инженерами, CSV — 5 МБ. Не добавлены сложные прогнозы, ретроспективное восстановление удалённых данных и фоновые предрасчёты.
