Шаг 12 — поиск, фильтрация, сортировка и пагинация заявок. Завершено 28 октября 2026.

**Результат.** Три списка заявок используют общий серверный обработчик Prisma, общий интерфейс фильтров и серверную пагинацию. Права доступа, SLA, комментарии, вложения и уведомления сохранены. Данные не сбрасывались и не удалялись, кроме точных записей, созданных тестами.

**API:** `GET /api/tickets`, `GET /api/engineer/tickets`, `GET /api/admin/tickets`. Все требуют JWT. `/api/tickets` всегда ограничен владельцем из JWT, включая total и summary. Engineer/admin проверяются по актуальной роли из БД и сохраняют существующий доступ к общей очереди. Подмена ownerId, recipientId или других неизвестных query-полей отклоняется. Обязательное ограничение доступа объединяется с поиском через AND, поэтому поисковые OR-условия его не обходят.

| Параметр | Значение |
| --- | --- |
| search | До 100 символов; title и description без учёта регистра; число или #число также проверяется как ID |
| status | new, in_progress, resolved; all или отсутствие — без фильтра |
| priority | low, medium, high; all или отсутствие — без фильтра |
| assignedEngineerId | Только engineer/admin: положительный ID, me, unassigned, all |
| dateFrom/dateTo | YYYY-MM-DD; календарные дни UTC; dateTo включительно, через верхнюю исключающую границу следующего дня |
| slaStatus | on_time, approaching_deadline, overdue, met, breached, unknown, all |
| slaStage | response, resolution, any; сохранён из Шага 11; any означает совпадение хотя бы одного этапа |
| sortBy | createdAt, updatedAt, priority, resolutionDueAt, nearestDeadline |
| sortOrder | asc/desc; обычно desc по умолчанию, для дедлайнов asc |
| page | 1 по умолчанию; положительное целое, не более 1 000 000 |
| limit | 10 по умолчанию; разрешены 10, 20, 50 |

Приоритет сортируется по смыслу low → medium → high для ASC, в обратном порядке для DESC. resolutionDueAt — хронологический порядок с null в конце. nearestDeadline — ближайший срок **решения**, активные заявки перед решёнными, null в конце своей группы; эта политика сохраняет сортировку срочности Шага 11. Во всех случаях ID — дополнительный стабильный ключ.

Поиск использует типизированные Prisma where и параметры ORM, без новых raw SQL. Символы `%`, `_` и обратная косая черта экранируются для буквального поиска, а не расширения LIKE. Слишком длинные строки, повторяющиеся параметры-массивы, некорректные ID/даты/диапазоны, значения вне allowlist и неизвестные параметры возвращают 400. Поиск администратора по имени/email автора или инженера сохранён как дополнительная совместимость с прежним интерфейсом.

**Ответ:**

```json
{
  "items": [],
  "page": 1,
  "limit": 10,
  "pageSize": 10,
  "total": 0,
  "totalPages": 0,
  "summary": {
    "total": 0,
    "new": 0,
    "in_progress": 0,
    "resolved": 0,
    "assignedToMe": 0
  }
}
```

items содержит безопасные данные заявки, SLA и разрешённые поля автора/назначенного инженера; пароли, токены, storageKey и приватные пути не выбираются. total соответствует всем фильтрам. Пустая выборка или страница за пределами результата возвращает пустой items. summary — отдельные агрегаты **всей доступной очереди**, независимо от фильтров; dashboard больше не считает статистику по одной странице. Для пользовательского endpoint summary также ограничен только собственными заявками.

Прежние массивы ответов user/engineer заменены указанным объектом. Все известные frontend-потребители обновлены, включая DashboardPage. Admin сохраняет прежний items/total/page/totalPages и alias pageSize. Для старых admin API-клиентов параметр pageSize 1–100 остаётся ограниченным legacy alias; при одновременном limit/pageSize возвращается 400. В новом UI используются только limit 10/20/50. Прежний sort=newest|resolutionDueAt поддерживается как alias; legacy resolutionDueAt сохраняет active-first поведение. Одновременно sort и sortBy передавать нельзя. slaStage и быстрые ссылки из SLA Analytics работают.

**Производительность.** SLA-фильтры переведены из выборки кандидатов в память в Prisma-предикаты PostgreSQL до count/skip/take. Завершённые этапы сравниваются с полем deadline через Prisma field references; ожидающие этапы — с одним зафиксированным серверным now и настройками SLA. Все 18 комбинаций SLA-статуса/этапа проверены на совпадение с существующим SLA service.

count и findMany используют одинаковый where. Они выполняются в RepeatableRead transaction, чтобы метаданные и строки одной страницы соответствовали одному снимку. Для обычных сортировок используется skip/take. Для семантического приоритета и active-first срочности используются несколько ограниченных SQL-групп: count позволяет пропустить целую группу, findMany получает только оставшуюся часть страницы. Таблица не материализуется в память, суммарное число загруженных строк не превышает limit. Это дополнительно проверено перехватом findMany внутри реальной транзакции. Серверные сводки строятся через groupBy/count, а не загрузку всех заявок в браузер.

**Миграция:** `20261028093000_ticket_list_indexes`. Добавлены только два B-tree индекса:

- Ticket(userId, createdAt, id) — собственные списки, диапазон дат и стабильная пагинация;
- Ticket(createdAt, id) — общая очередь по времени создания.

Индексы status/responseDueAt и status/resolutionDueAt из Шага 11 переиспользуются. Дополнительные поля и изменения рабочих записей не требовались. Миграция применена через migrate deploy; старые миграции и SLA-дедлайны не менялись; migrate reset не запускался. migrate status — актуально, migrate diff — No difference detected.

**Frontend.** Общие TicketFilters, TicketPagination, TicketList и useTicketList используются на user/engineer/admin списках. Есть поиск, статус/приоритет, даты UTC, SLA и этап, сортировка, направление, limit, страницы, total и сброс. Фильтр инженера есть у admin. Контекст «Назначено мне» инженера передаётся серверу через assignedEngineerId=me, а не фильтрует загруженную страницу в браузере. Сброс сохраняет этот контекст, если пользователь находится в нём; переход «Все» снимает его.

Фильтры и страницы находятся в URL; изменение фильтра сбрасывает page. Поиск отправляется после debounce 350 мс. Старый запрос отменяется AbortController; дополнительно результат проверяется по сигналу и ключу текущего запроса. Поэтому даже транспорт, игнорирующий abort и возвращающий старый ответ позднее, не заменяет новый результат. Старые строки скрываются сразу при новом query. Реализованы loading/empty/error/retry. JWT берётся из auth context и передаётся только в Authorization. URL его не содержит. Переходы деталей сохраняют маршруты соответствующей роли. Дизайн и SLA-компоненты переиспользованы; адаптивность 360px проверена.

**Ручная проверка:**

1. Запустите backend/frontend через npm.cmd run dev, войдите в соответствующую роль и откройте /tickets, /engineer или /admin/tickets.
2. Введите часть названия/описания или #ID. После паузы около 350 мс проверьте результат и search в URL.
3. Перейдите на вторую страницу, поменяйте фильтр — page должен сброситься. Выберите 20 или 50 записей, проверьте total и переходы страниц.
4. Совместите статус, приоритет, даты UTC и SLA. В admin выберите инженера. Проверьте сортировку и быстрые ссылки из SLA Analytics.
5. Обновите страницу или откройте тот же URL под той же ролью: фильтры должны сохраниться. JWT в адресе отсутствует.
6. В DevTools включите медленную сеть, быстро смените поиск: устаревшая выдача не должна заменять новую. Для предсказуемой проверки игнорирования abort используйте автоматический браузерный тест.
7. Нажмите «Сбросить фильтры», проверьте пустой поиск, откройте детали. Повторите при ширине 360px.
8. Для проверки удаления не используйте рабочие данные: автоматические тесты самостоятельно создают и очищают свои записи.

**Ограничения.** Нумерованная пагинация использует offset: изменение данных между двумя разными запросами страниц может сдвинуть позиции; стабильный ID решает неоднозначность одинаковых значений, но не замораживает всю очередь между запросами. Очень большие offset и substring ILIKE-поиск могут требовать дальнейшей оптимизации, например cursor pagination и согласованных trigram-индексов. Поиск по ID добавляет ID к текстовым условиям, а не исключает текстовые совпадения. Диапазон дат использует дни UTC, что явно подписано в интерфейсе. Отдельная аналитика SLA Шага 11 не переписывалась; списки и SLA-фильтры больше не загружают таблицу в память. Старым внешним клиентам, ожидающим массив user/engineer, необходимо перейти на items нового ответа; все потребители проекта обновлены.
